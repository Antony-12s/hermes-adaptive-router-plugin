# Decisions

- The Desktop interface lives in the unified HARP package, not as a second routing owner. It uses HARP's own authenticated Dashboard API and never calls the account-pool plugin.
- Desktop enablement is opt-in and separate from the Python plugin gate. Missing `HARP_CONFIG` leaves routing inactive; the page explains the missing usage collection without inventing defaults.
- The local daily token budgets remain observational. Quota is shown per account: each row carries its own session and week windows from HARP's read of that pool credential (read automatically when the page opens, at most every 5 minutes, and on Live usage). There is no separate shared provider-quota table.
- The Desktop view follows Accounts' compact header, summary cards, status-marked account rows, and quota meters.
- HARP owns four account actions on the Hermes credential pool: Live usage (read-only per-credential usage), Balance now (bench at 90% or more, never the whole pool below 100%, release HARP benches, order by usage; no change without readings), Wake (Anthropic only, one 1-token request to accounts whose session window is idle, 10-minute cooldown), and Add account (relays Hermes' own `hermes auth add`; tokens never reach HARP or the renderer). Balance and Wake require confirmation in the page.
- Row actions are HARP-owned too: sign in again (new login takes the old label, position and schedule; the old login is deleted only after success), park (Hermes pool hold with reason `harp-parked`, optional end time), weekly park schedules applied by `hermes harp tick` from a per-user Task Scheduler task "HARP Timer" (installed while any schedule or alert channel is on, removed when none is), and remove (confirmed). Tokens, 24 h and Used by come from HARP's own post_api_request tracker (`harp-activity.sqlite3`), which counts from installation onward.
- HARP balance marks its benches with `[HARP balance]` and releases only its own benches. Run only one balance owner at a time; the account-pool balance timer was inactive when this was added.
- Page layout: the top row picks Diagram or a provider (Type-safe = jev, anthropic, Codex); the second row picks Accounts & usage, Activity, Report, Health or Alerts. Activity is HARP's own change log (30 days). Report groups HARP-tracked tokens by account, model, source and session, with a 7-day hourly heatmap and, when the timer records usage snapshots, each account's peak and minutes at 90% or more. Health runs checks from local state only. Alerts send Windows notifications and/or Telegram (`hermes send`) once per condition; the HARP Timer reads usage every 5 minutes only while an alert channel is on.
- Type-safe (jev) accounts are API keys, not sign-ins. Add account asks for a name and a masked key, checks it with TypeSafe's free GET /v1/models, and only then saves it to Hermes' pool (creating providers.jev with base_url https://api.typesafe.ai/v1 on first use). Replace key keeps the entry's name, position and schedule. TypeSafe has no usage or balance API, so Live usage is a key check and Balance/Wake are off for Type-safe; spend is in the TypeSafe console.
- Router (Diagram tab): each new message gets a pick of provider, model and effort. A working Jev (Type-safe) key makes Jev decide whatever the local learner is unsure about and teaches it; with no key, a rejected key, or Jev down, the local learner (TF-IDF over character n-grams, works for Thai) decides alone. It learns from Jev's answers and from the user's Right/Wrong feedback, and user-confirmed messages are sent back to Jev as examples. Provider load = each account's plan weight (x1/x5/x20) times its unused share; work moves off a provider above the limit. Default is Shadow (record only). Apply only rewrites model and effort on the session's own provider through llm_request middleware, using Hermes' own Anthropic thinking mapping; cross-provider switching is not done because the hook cannot change provider. Jev calls are capped per day (300 default).
- Tokens card gained an estimated $ cost and a request count, computed from the calls table (model+tokens) with a rough blended $/1M-token table in pool_state.estimate_price (opus/sonnet/haiku/fable, gpt-6 family, mini); unknown models show no price line. requests_24h and price_24h ride on get_accounts next to tokens_24h.
- Summary tab (first in the top row): every provider at a glance. Cards for tokens/cost/requests across all providers, usable accounts, the account+window with the least left (with countdown), and Jev state. One section per provider: anthropic and Codex show remaining % (100 - used) per 5-hour and weekly window with its own reset countdown; Type-safe shows the key check. It reuses /accounts per provider and the same 5-minute read-only live refresh as the provider tabs.
- Summary tab gained an Activity heatmap (GitHub-style hour x day grid, Week/Month toggle) combining token counts across every provider: dashboard.pool_state.combined_chart(db, providers, days) generalizes the per-provider _chart to any day count; endpoint GET /activity/heat?span=week|month.
